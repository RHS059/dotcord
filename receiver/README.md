# Dedicated Dotcord receiver

This is a separate OAuth-connected Sites app for **one receiving Dot**. Keep the shared Dotcord page for accounts, handles, Discord settings and sending. Give each receiving Dot its own deployment of this small companion, with its own connector identity. Selecting that connector selects its pinned recipient instead of relying on the shared connector's ambiguous account selection.

The companion does not implement an OAuth authorization server or manufacture a ChatGPT wake URL. Sites provides OAuth and trusted identity; the receiving platform supplies the callback and signing secret when it creates a `dot.mentioned` task. The companion forwards that registration to the shared app using a scoped, expiring receiver credential. Shared Dotcord stores the verified destination and sends mention events directly to it. No callback data is stored in this companion, and it needs no database.

## Build and configure

1. Deploy this folder as a **new private Sites project for the receiving Dot**, with a distinct connector. Run `npm run build` from `receiver/`. The artifact is `receiver/dist/`. Copy `.openai/hosting.example.json` to the ignored `.openai/hosting.json`, add the newly provisioned `project_id`, and rebuild before publication. Do not reuse the shared app's project ID or connector.
2. Through that project's trusted host sign-in, open `/api/identity`. Set private runtime `RECEIVER_SUBJECT` to that exact authenticated subject. Subjects differ across Sites: do not copy the shared app's account ID. This bootstrap route returns only the visitor's own subject; no paired account data or secrets. Restrict the Site's audience to the intended receiving account and authorized administrator. Once pinned, another connection cannot manage the receiver.
3. In shared Dotcord, authenticate as the intended recipient and create a receiver credential. Configure that value privately as `DOTCORD_RECEIVER_TOKEN`, and configure `DOTCORD_ORIGIN` as the exact shared app HTTPS origin (no trailing slash, path, query or fragment). This explicit credential pairing binds the companion to the canonical shared account without guessing from email, handle or cross-app subject IDs. Never paste credentials into source, Git, prompts, screenshots or public settings.
4. If the shared Site's private access gate requires service access, obtain its platform-supported service-access bearer through the authorized Sites setup and set private `DOTCORD_SITES_TOKEN`. It is sent only to the configured exact origin as `OAI-Sites-Authorization: Bearer …`. It grants hosting entry, not application identity. The separate `Authorization` header carries the receiver credential. An access denial must be corrected using supported host configuration; this app has no proxy or fallback route.
5. Connect **this dedicated receiver connector** in the receiving platform. Call `get_receiver_status` and compare the returned account binding with the intended shared Dotcord account. Create its `dot.mentioned` task with empty arguments `{}`. Check `receiver_ready` and `receiver_subscriptions` afterward: the account-level `state` can also reflect another native subscription and does not by itself prove this receiver is registered. The platform must supply the callback, complete verification, and renew the subscription before `refreshBefore`. Keep only the intended connection on this dedicated connector; incorrect identities fail closed.
6. Verify an authorized end-to-end mention and actual receiving-agent execution. The event contains the message. Pending inbox reads and acknowledgments use the shared Dotcord app's existing tools; this companion exposes only `get_receiver_status` and the event subscription interface.

Runtime configuration is not read from `.env.example`; use the host's private settings. If you do not need service access, omit `DOTCORD_SITES_TOKEN` entirely. Rotate the scoped credential before expiry, and revoke it if the receiver is retired. The shared account's current access policy still applies.

## Security and limitations

Only run behind the Sites gateway that authenticates callers, strips untrusted `oai-authenticated-user-*` headers and prevents direct Worker access. The Worker trusts the gateway and is unsafe on a raw public Worker URL. No Google-client secret is needed here: this companion uses its own Sites OAuth connection.

All subscription/status actions require the exact configured receiver subject. Discovery reveals static schemas only. Browser-origin MCP calls must be same-origin. The companion rejects account/handle filters, forwards no inbound identity headers or cookies, pins one HTTPS upstream origin, refuses redirects, bounds JSON and request times, and never logs credentials or callback content. Upstream application errors retain their JSON-RPC code and message.

This design removes shared-connector account ambiguity by using distinct connectors. It does not create a task upon login, select a connection inside the platform, or guarantee subscription renewal. Each dedicated connector still needs initial platform task setup. Source tests use mocked requests; a successful build is not a verified sleeping-agent wake.
